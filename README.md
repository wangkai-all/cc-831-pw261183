# 公平工作包分配工作台

一个从空目录搭建的小型分配数据应用：虚构成员、不可拆工作包、资格、个人估时与个人成本；
用精确搜索比较 **最小最大负担**、**EF1（envy-free up to one item，移走一项后消除嫉妒）**
和 **总成本**，并把成员接受后的承诺台账接入重算与解释页面。

后端只使用 Python 标准库；前端是原生 HTML/CSS/JavaScript，没有外部图表库或 CDN 依赖。

## 启动

```bash
./scripts/run.sh
# 或
HOST=127.0.0.1 PORT=8000 python3 -m app.server
```

打开 <http://127.0.0.1:8000/>。

运行测试：

```bash
python3 -m unittest discover -s tests -v
```

测试包含独立笛卡尔枚举、最优界核对、EF1 手算样例、同包/互斥、资格无解集合、
承诺锁/承诺冲突、台账持久化和 HTTP 冒烟。

## 页面能做什么

- 在五个虚构场景间切换：
  - `studio`：5 人 9 包，含资格、同包绑定、互斥职责分离、异质估时和一条示例承诺。
  - `tradeoff`：3 人 6 包，三个目标的最优安排互不相同。
  - `micro`：2 人 4 包，共 \(2^4=16\) 种原始分配，页面可逐行枚举核对。
  - `constraint_lab`：同包 + 互斥 + 故意写入的承诺冲突。
  - `qualification_gap`：硬资格无解，给出具体无资格包和无共同资格的同包集合。
- 同时比较三类精确最优方案。
- 查看成员负担条形图、容量线、使用率和个人成本。
- 在“为什么羡慕？”中选择观察者和另一成员，查看：
  - 观察者用**自己的估时**如何评估两个束；
  - 嫉妒差；
  - 移走自己束中哪一项可以/仍然不能消除嫉妒；
  - 每个候选移走项后的残差。
- 在看板中接受并锁定某个任务，或用台账表单手动把任务记给某成员（可复现承诺冲突）。
- 调整任意成员容量并对比原容量/试算容量下的最优值和安排。
- 对小实例运行独立枚举，显示可行数、不可行原因和求解器 key 是否与枚举最优一致。

## 建模口径

设成员 \(i\) 对工作包 \(p\) 的个人估时为 \(h_{p,i}\)，个人成本为 \(c_{p,i}\)
（示例数据中多数成本由虚构成本单价 × 本人估时得到，数据结构也支持显式成本矩阵）。
每个成员对同一包还有不同的 1–5 难度感受 `difficulty[p][i]`，页面会显示该观察者口径；
难度评级只用于解释“为什么估时因人而异”，不会在容量公式中被悄悄乘成另一个硬指标。
安排 \(A\) 给成员 \(i\) 的束为 \(A_i\)。

### 硬约束

求解器绝不通过修改估时、资格或容量来“凑可行”。硬约束包括：

1. 每个工作包恰好分配给一名成员，工作包不可拆分。
2. 成员必须具备工作包要求的全部资格。
3. 本人估时负荷不得超过其容量：

   \[
   \sum_{p\in A_i} h_{p,i} \le K_i.
   \]

4. `together` 组中的工作包必须由同一人完成。
5. `exclusive` 组中的任意两个工作包不能由同一人完成。
6. 台账中已接受的 `(package, member)` 是承诺锁；重算只能改变未接受项。

同包约束先用并查集压缩成 block；若 block 中已有承诺给不同成员，返回具体工作包集合，
例如 `{c1,c2}`，错误码为 `commitment_conflict_inside_together_block`。

硬资格无解时返回具体集合：

- 没有任何成员满足合并资格的单个包：`package_ids: ["g1"]`；
- 每个包单独有人可做、但同包后没有成员具备全部资格：`package_ids: ["g5","g6"]`。

### 负担与嫉妒

成员 \(i\) 的实际负担按 \(i\) 自己的估时计算：

\[
B_i(A)=\sum_{p\in A_i} h_{p,i}.
\]

最小最大负担目标主值为：

\[
\min_A \max_i B_i(A).
\]

页面另外展示 \(B_i/K_i\) 容量使用率，但没有把归一化口径混入上述经典最小最大目标。

嫉妒评价也使用观察者 \(i\) 的估时。对 \(i\to j\)：

\[
V_i(A_i)=\sum_{p\in A_i}h_{p,i},\qquad
V_i(A_j)=\sum_{p\in A_j}h_{p,i}.
\]

因为这是家务/负担分配，\(V_i(A_i)>V_i(A_j)\) 表示 \(i\) 认为 \(j\) 的束对自己更轻松，因而羡慕 \(j\)。

家务型 EF1 的口径是：存在 \(p\in A_i\)，从羡慕者自己的束中移走该项后不再嫉妒：

\[
V_i(A_i\setminus\{p\})\le V_i(A_j).
\]

最有利的一次移走是移走 \(i\) 估时最大的项，因此系统计算：

\[
R_{i,j}=V_i(A_i)-\max_{p\in A_i}h_{p,i}-V_i(A_j).
\]

\(R_{i,j}\le 10^{-9}\) 时该有序对满足 EF1。优化 `ef1` 目标时按以下词典序最小化：

1. 违反 EF1 的有序对数；
2. 最大 EF1 残差小时数；
3. 残差小时数总和；
4. 嫉妒对数、最大负担和成本（确定性 tie-break）。

### 总成本

\[
C(A)=\sum_i\sum_{p\in A_i}c_{p,i}.
\]

## 目标可能冲突

`tradeoff` 场景由独立枚举核对，三个目标的最优安排确实不同：

| 目标最优解 | 最大负担 | 总成本 | EF1 | 最大“移一项后”残差 |
|---|---:|---:|---|---:|
| 最小最大负担 | **11h** | ¥3,700 | 不满足，1 对违反 | 1h |
| EF1 最优 | 14h | ¥3,500 | **满足** | 0h |
| 总成本最优 | 13h | **¥3,440** | 不满足，1 对违反 | 3h |

因此不存在一个指标能代表所有公平/效率诉求；页面把三条边界并列展示。

## 承诺与公平损失

台账是 append-only JSON，默认路径：

```text
ledger/acceptance-ledger.json
```

可通过环境变量 `ALLOC_LEDGER` 覆盖（测试使用临时文件）。

`studio` 的示例承诺是陈禾（`m3`）已接受 `p_api`。同一最小最大负担目标下：

- 忽略承诺的自由最优：最大负担 **21h**；
- 锁定 `p_api → m3` 后：最大负担 **24h**；
- 承诺造成的主目标损失：**+3h**。

系统对每个目标分别计算 free vs committed 的差值。若承诺集合本身冲突，
例如 `constraint_lab` 种子中 `c1→m1`、`c2→m2`，而 `c1/c2` 必须同人，
接口返回 `feasible:false` 和精确冲突包集合，不会移动任一已接受项。

普通 `/api/acceptances` 不能把同一工作包改给另一位成员，会返回 `409 commitment_already_exists`；
同一成员重复接受是幂等的。演示中要改承诺，请“清空/恢复示例台账”，或在受信任请求中显式传
`"supersede": true`（会留下 supersede 记录）。

“恢复示例台账/清空承诺”是显式演示管理操作；正常重算和页面接受操作不会撤销已有承诺。

## HTTP API

| 方法与路径 | 说明 |
|---|---|
| `GET /api/scenarios` | 场景摘要 |
| `GET /api/scenario?id=studio` | 完整虚构数据与台账记录 |
| `POST /api/compare` | 一次返回 free/committed × 三目标 × 原容量/试算容量 |
| `POST /api/solve` | 单目标精确求解 |
| `GET /api/enumerate?scenario=micro` | 小实例笛卡尔枚举、硬约束检查和最优界交叉核对 |
| `GET /api/envy?...` | 单独解释某个有序对（页面通常直接使用 solve/compare 内的解释） |
| `GET /api/ledger?scenario=studio` | 台账记录与当前有效锁 |
| `POST /api/acceptances` | 追加接受记录 |
| `POST /api/ledger/clear` | 清空指定场景（演示管理） |
| `POST /api/ledger/reset` | 恢复种子台账 |

`POST /api/compare` 示例：

```bash
curl -sS http://127.0.0.1:8000/api/compare \
  -H 'Content-Type: application/json' \
  -d '{"scenario":"studio","capacity_overrides":{"m3":30}}'
```

## 精确性与规模边界

当前求解器面向教学设计中的小/中实例：

- 同包 block 上的完整 DFS；
- 容量和互斥边剪枝；
- 每个可行叶节点都计算完整指标并比较词典序 key；
- 返回节点数、可行叶数、剪枝数和 `proven_optimal: true`。

`micro` 与 `tradeoff` 另有未压缩的原始分配枚举，测试中把枚举最优 key 与 DFS key
逐项对比。页面枚举接口默认设置 4096 个原始分配的安全上限；更大的 `studio`
应使用 DFS，而不是全量笛卡尔枚举。
